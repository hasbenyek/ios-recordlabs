## 3. Completed Unread Areas

### 3.1 `po_token.html` and its Android host (`PoTokenWebView.kt`, `JavaScriptUtil.kt`, `PoTokenException.kt`, `PoTokenResult.kt`, `PoTokenGenerator.kt`)

**Confirmed from source, full read.** The mechanism is a 3-phase native↔JS handshake:
1. **Create**: native OkHttp `POST https://www.youtube.com/api/jnn/v1/Create` with a fixed public request key (`O43z0dpjhgX20SCx4KAo`) → response is parsed (`JavaScriptUtil.parseChallengeData`, handling YouTube's "descrambling" scheme: base64-decode, +97 to every byte, re-decode UTF-8) into a challenge object injected as a JS literal, then `evaluateJavascript("runBotGuard(data)...")`.
2. `runBotGuard` (in `po_token.html`) loads the **actual BotGuard VM interpreter fetched at runtime** from the Create response (`challengeData.interpreterJavascript...`, executed via `new Function(interpreterJavascript)()`) — **the real BotGuard bytecode is never bundled in the app; it's always fetched fresh from Google.**
3. **GenerateIT**: native `POST .../jnn/v1/GenerateIT` with the BotGuard-produced attestation → integrity token → `evaluateJavascript("createPoTokenMinter(...)")` → per-videoId `obtainPoToken(identifier)` calls mint the actual token bytes, base64url-encoded natively.

`po_token.html` itself (214 lines) is a **hand-written driver/harness** matching Google's real `BgUtils` client library calling convention — not a vendored copy of BotGuard, not a reimplementation of the VM. Bridge: Android's `addJavascriptInterface` exposes 6 named `@JavascriptInterface` methods (`downloadAndRunBotguard`, `onJsInitializationError`, `onRunBotguardResult`, `onMinterCreated`, `onObtainPoTokenError`, `onObtainPoTokenResult`).

**iOS portability verdict:**
- **Portable as-is**: all native networking (pure OkHttp → trivially `URLSession`), the JS itself (plain ECMAScript, no Chromium-only syntax detected), timeout/retry/session-caching logic in `PoTokenGenerator` (8s per-call / 45s init timeouts, permanent-disable-on-`BadWebViewException` heuristic keyed on the substring `"SyntaxError"`).
- **Requires real redesign, not a drop-in port**: `addJavascriptInterface`'s multi-method-named-object pattern has **no WKWebView equivalent** — `WKScriptMessageHandler` only gives one-way `postMessage(body)` per handler name, so the 6 bridge methods need to become 6 registered handler names (or one handler + a `{method, args}` envelope). Similarly, `WebChromeClient.onConsoleMessage`'s `"Uncaught"`-substring JS-error detection has no WKWebView equivalent — must inject a `window.onerror` shim from scratch, since WKWebView has no console-observation API prior to `isInspectable` (iOS 16.4+, and that's for Safari Web Inspector attachment, not programmatic capture).
- **The single biggest unknown, unresolvable from source**: whether Google's **remotely-fetched, opaque** BotGuard interpreter performs Chromium/V8-specific environment fingerprinting that would make it behave differently (or get rejected server-side) under JavaScriptCore/WebKit even with a spoofed Chrome `User-Agent`. This cannot be answered by code review — it can only be answered by actually running it, which requires Phase 0 (§8 below) to happen first.

### 3.2 LyricsPlus & OpenRouterStreamingService

**Confirmed from source, full read.**
- **LyricsPlus** queries two *independent* backends per lookup: a pool of 4 failover mirror URLs (`lyricsplus.binimum.org`, `.atomix.one`, `.prjktla.my.id`, `.vercel.app`, sticky-cached "last working" reordering) for JSON word/line-sync lyrics, plus a wholly separate "Binimum" search API (`lyrics-api.binimum.org`) that returns TTML via a search→pick-result→fetch-URL indirection, parsed by the **same shared `TTMLParser`** the BetterLyrics provider uses. Priority: Binimum-word-sync first, then LyricsPlus, with Binimum-line-sync as a fallback if LyricsPlus doesn't also produce word-sync. No auth/API keys anywhere — pure unauthenticated REST, trivially portable.
- **Real finding — duplicated logic**: `LyricsPlusProvider.convertToLrc` and `TTMLParser.toLRC` are **two independently-written implementations** of the same agent-tagging/LRC-emission algorithm (with subtly different edge-case behavior — e.g., `TTMLParser.toLRC` force-tags multi-agent when a lone `v1` singer has any background line, `convertToLrc` doesn't). Two separate `formatLrcTime` functions also exist. **Recommend consolidating to one Swift LRC-emission function during the port, not porting the duplication forward.**
- **OpenRouterStreamingService**: manual line-by-line SSE parsing (`data: ` prefix, `[DONE]` sentinel) over a blocking `BufferedReader`, not a dedicated SSE library — ports naturally to `URLSession.bytes(for:)`'s `AsyncSequence`. The "partial JSON streaming parser" (`LyricsTranslationHelper.tryParsePartialTranslation`) is, on inspection, **not actually JSON-aware at all** — it's a naive newline-split + 3-regex-prefix-strip heuristic used only for a live preview; the real, authoritative parsing is the separate 4-tier fallback string→array parser (`parseTranslationContent`), which is what needs a faithful port.
- **Real finding — feature-parity gap already exists on Android**: the streaming translation path has **no `"Romanized"` prompt mode** and **no retry-on-5xx**, both of which the non-streaming path has. Decide intentionally whether iOS should unify these (recommended) rather than porting the inconsistency forward.

### 3.3 BetterLyrics TTML edge cases & lyrics persistence DAO paths

**Confirmed from source, full read**, including the existing 14-test unit test suite (`TTMLParserTest.kt`).
- **Malformed XML** → the entire `parseTTML` call is wrapped in one blanket `try/catch`; any parse failure returns `emptyList()` — no partial parse, no per-line recovery.
- **Real bug-equivalent finding**: a `<p>` line with **no timing anywhere** (no `begin`, no `ttp:begin`, no child span with `begin`) is **silently dropped** — `findFirstSpanBegin` returns `null`, `parseP` hits an Elvis `return`, and the line vanishes with no log, no placeholder, no error. Not exercised by any existing test.
- **Real bug-equivalent finding**: the v1/v2 agent-remapping algorithm has a **shared, never-reset `nextNum` counter** across the whole line list. A 3rd distinct singer/agent (anything beyond the canonical `v1`/`v2`/`v1000`) **silently collapses into `{agent:v1}`** once both slots are taken — verified by direct code reading (not test-covered on Android either). `v1000` gets an explicit "map to v2 if v1 taken" special case; no other alias (e.g. `v2000`) gets that treatment, it just falls through the generic slot-filler.
- **`parseTime()`** never throws — any unparseable time string (including pure garbage) silently becomes `0.0`, which can cause unrelated lines to collide at `[00:00.00]`.
- **Nested spans**: only 2 levels are manually walked (`<p>` → `x-bg` span → direct-child word spans); a 3rd level of nesting has its text silently absorbed into the parent span via DOM `textContent`, losing fine-grained timing without error.
- **Lyrics DAO**: `LyricsEntity` is keyed **only by song id**, not by provider — confirmed by an explicit in-code comment on `clearAllLyrics()` documenting this exact limitation. The **only** cache-eviction mechanism is a **manual whole-table wipe**, triggered by 6 UI call sites (toggling any lyrics provider on/off, or reordering provider priority) — there is no TTL, no per-row expiry, no "does this look wrong, refetch" heuristic. First write happens on-demand (viewing the lyrics screen, 500ms debounce) or on download-completion (a dedicated offline-prefetch path); a third trigger path gated on `ShowLyricsKey` is **confirmed dead code** — that preference is never written anywhere in the app, so that branch never fires.
- **iOS implication**: replicate the "provider-order-change ⇒ wipe whole cache" behavior (or improve it with a provider-aware cache key, recommended), and explicitly decide whether to port the untimed-line-drop and 3rd-agent-collision behaviors as-is or fix them — both are new, previously-unflagged findings from this pass, not carried over from V1.

### 3.4 Download implementation & actual media formats

**Confirmed from source, full read — this directly answers item 6 (§6 below).**
- Two nearly-identical `ResolvingDataSource.Factory` instances exist: one in `MusicService` (streaming, checks `downloadCache` then `playerCache`) and one in `DownloadUtil` (download-initiation, checks only `playerCache`) — both call the same `YTPlayerUtils.playerResponseForPlayback`, so format-selection logic is identical between streaming and downloading.
- **Downloads are Media3 `SimpleCache`/`DownloadManager` byte-range fetches of the resolved adaptive-format URL, stored as opaque cache-span files keyed by video ID — no file extension, no container metadata on disk.** Grep for `Muxer|remux|transcod` across the entire codebase: **zero matches.** Confirmed: raw YouTube adaptive-format bytes are stored completely unmodified.
- **Format**: audio-only formats only (`isAudio` filter applied unconditionally); codec preference is opus > mp4a when quality/channel-count tie, with quality-label and bitrate as the primary sort keys. Exact common-case container/codec (e.g. `audio/webm; codecs="opus"` vs. `audio/mp4; codecs="mp4a.40.2"`) is **not a literal string constant anywhere in the codebase** — it's whatever YouTube's API returns for a given client/video, scored generically.
- **Protocol confirmed**: plain progressive HTTP(S) GET/range-requests against a resolved `googlevideo.com` CDN URL. **No HLS `.m3u8` manifest, no DASH manifest, no DRM/FairPlay anywhere in the download or playback data-source chain.**
- **`isVideo` flag confirmed to be UI-only** — every playback/download path filters to audio-only formats unconditionally regardless of this flag; there is no video-stream download or playback path anywhere in the app.

### 3.5 EQ DSP internals & AutoEQ parser/repository

**Confirmed from source, full read.**
- `BiquadFilter.kt`: standard RBJ Audio EQ Cookbook coefficient formulas, verified line-by-line — Peaking, Low-Shelf, High-Shelf all match the canonical formulas exactly. Pure `kotlin.math`, zero Android dependency — **directly portable Swift math**, drop-in for an `AVAudioEngine`/`MTAudioProcessingTap` render callback.
- **Real gap found**: `FilterType` enum declares 5 values (`PK`, `LSC`, `HSC`, `LPQ`, `HPQ`), and `ParametricEQParser` parses all 5 from AutoEQ text files — but `BiquadFilter` only implements coefficient math for `PK`/`LSC`/`HSC`; `LPQ`/`HPQ` **silently fall back to peaking-filter math** via an `else` branch. This is a genuine, previously-unflagged functional gap in the *Android app itself* — decide during the iOS port whether to implement true low-pass/high-pass RBJ formulas (better) or preserve this fallback for output parity (worse, but matches existing behavior).
- `ParametricEQParser.kt`: pure regex/string parsing of the standard AutoEQ `Filter N: ON <type> Fc <freq> Hz Gain <gain> dB Q <q>` format, with silent per-line skip on malformed input (never throws except on missing file). Directly portable.
- `EQProfileRepository.kt`: **correction to V1's inferred description** — the exposed type is `StateFlow<SavedEQProfile?>`, not a generic `Flow`. Confirmed exact `SharedPreferences` namespace (`nanosonic_eq_profiles`) and keys (`eq_profiles`, `active_profile_id`), plaintext JSON array blob. Schema/CRUD logic is portable; the I/O layer (SharedPreferences, Hilt DI) is not and needs a full iOS rewrite against `UserDefaults`/`Codable`.
- `GitHubAutoEqSearch.kt`: unauthenticated GitHub Trees API + raw-content fetches against **`ndellagrotte/AutoEq`, a fork, not the canonical `jaakkopasanen/AutoEq` upstream** — worth flagging to the user before porting this URL forward, since a fork can silently diverge from canonical AutoEQ data. 24h cache TTL with stale-fallback-on-failure; no rate-limit handling (relies on the low request volume + long TTL to stay under GitHub's unauthenticated 60/hr limit). Search/cache/rig-resolution algorithms are pure logic and portable; only `OkHttpClient`/`Context.filesDir`/logger need iOS-native swaps.

### 3.6 `handleAlarmTrigger` and boot/time-change resilience

**Confirmed from source, full read — this materially changes the risk assessment from V1 §30.**
- **Real finding: Android's "Music Alarm" has no actual alarm-clock behavior to replicate.** It plays over the ordinary `USAGE_MEDIA` audio stream at whatever the current volume is — confirmed **zero** uses of `AudioManager.STREAM_ALARM`/`AudioAttributes.USAGE_ALARM`/`setStreamVolume` anywhere in the codebase, **zero** volume ramp/fade-in, **zero** Do Not Disturb or ringer-mode interaction. If the phone is silenced, the "alarm" plays silently with no OS-level override.
- Missing-or-emptied playlist is handled gracefully: the alarm **self-disables** (sets `enabled=false`) rather than crashing or looping — confirmed for both the "playlist ID blank" and "playlist exists but has zero songs" cases (both produce the same effect, since Room can't distinguish "deleted" from "emptied" playlists at this query).
- "Random song" is **not a real shuffle** — it only picks one random starting track and moves it to the front; the rest of the queue keeps original order.
- Uses `AlarmManager.setExactAndAllowWhileIdle`/`setAndAllowWhileIdle` + `RTC_WAKEUP` (not the stronger `setAlarmClock()` API), no weekday/repeat-schedule support (every alarm is "next occurrence, daily, no day-of-week filter"), and a confirmed-harmless-but-real **double reschedule** bug (the reschedule-all routine runs twice within one alarm firing).
- **iOS implication, revised from V1**: since Android's own implementation has no true alarm-clock behavior to match, the iOS gap is narrower than V1 suggested — the hard blocker is purely **"can iOS autonomously resume audio playback from a suspended/terminated app at a scheduled wall-clock time,"** which it fundamentally cannot (no `AlarmManager` equivalent). A scoped-down iOS version (local notification at the scheduled time, user taps to start playback) is not a "lesser" port of missing alarm-clock polish — Android doesn't have that polish either — it's specifically the *autonomous background wake* capability that has no iOS equivalent, full stop.

## 4. iOS Playback Architecture — Requirement-by-Requirement

| Requirement | Coexists with `AVPlayer`? | Mechanism |
|---|---|---|
| AVPlayer streaming | **Baseline** | Already the current architecture; no change. |
| Background playback | **Yes** | `AVAudioSession.Category.playback` + `UIBackgroundModes: [audio]` in `Info.plist`. **Confirmed currently absent** — `Info.plist` (read directly) has no `UIBackgroundModes` key at all; background audio would fail immediately without this being added. |
| `MPNowPlayingInfoCenter` | **Yes** | Standard, no engine dependency. |
| `MPRemoteCommandCenter` | **Yes** | Standard, no engine dependency. |
| Crossfade (two players) | **Yes** | Two independent `AVPlayer` instances play concurrently through the shared `AVAudioSession` — iOS mixes overlapping playback automatically; manual `player.volume` ramping (Timer/`CADisplayLink`) replicates Android's quadratic-ease dual-instance approach directly. **No `AVAudioEngine` needed.** |
| Gapless playback | **Best-effort only** | `AVQueuePlayer`/sequential `AVPlayerItem` insertion gives near-gapless transitions for many format pairs, but **not guaranteed sample-accurate** for network-streamed adaptive audio. True sample-accurate gapless needs `AVAudioEngine` with fully pre-decoded/scheduled buffers — which conflicts with progressive-URL streaming (you'd need to fully download+decode ahead of time, reimplementing what `AVPlayer`'s HTTP loading already does). **Recommend accepting best-effort parity**, consistent with the fact that Android's own "gapless" is itself just a heuristic that skips crossfade (§3, V1 §3) rather than a guaranteed bit-perfect join. |
| Equalizer | **Yes, via `MTAudioProcessingTap`** | Attach a Media Toolbox audio-processing tap to the `AVPlayerItem`'s audio track to intercept/modify raw PCM buffers in-place while `AVPlayer` still owns network/buffering/session management. The confirmed-portable `BiquadFilter` RBJ math (§3.5) plugs directly into the tap's render callback. **Not `AVAudioEngine`** — that would mean reimplementing streaming/buffering yourself. |
| Loudness normalization | **Yes, same `MTAudioProcessingTap`** | Same linear-gain-multiply-per-sample approach Android uses, ported into the same tap callback. |
| Silence skipping | **Yes, same tap** | Detection via the tap's PCM analysis; *acting* on it (skipping) is a `player.seek(to:)` call triggered from the detection callback — feasible, no engine swap needed. |
| Playback speed & pitch | **Yes, fully native — no tap needed at all** | `AVPlayerItem.audioTimePitchAlgorithm` (`.timeDomain`/`.spectral`/`.varispeed`) + `player.rate` is a direct, built-in analog to Android's `SonicAudioProcessor` — the simplest requirement on this entire list. |

**Bottom line**: **`AVPlayer` + `MTAudioProcessingTap` covers every DSP requirement** (EQ, normalization, silence detection); speed/pitch is entirely native; crossfade is two coexisting `AVPlayer`s with manual volume ramping. **`AVAudioEngine` is not required for anything Android actually does** — it would only become necessary if a future requirement demanded true sample-accurate gapless or custom decode of a format `AVFoundation` can't natively handle, at the cost of reimplementing network buffering yourself. Recommend explicitly **not** adopting `AVAudioEngine`, and accepting best-effort (not guaranteed) gapless as a deliberate, documented scope reduction.

**`MTAudioProcessingTap` caveats to flag**: it's an older Media Toolbox C-callback API (not a modern Swift-native API surface), requires careful render-thread/main-thread discipline, and needs one tap instance created/torn down per `AVPlayerItem` (i.e., per track and per crossfade-secondary-player) rather than one persistent global tap.

**A previously unflagged, concrete finding**: `StreamResolver.swift`'s current format selection (`sorted { $0.bitrate > $1.bitrate }`, no codec filter) will accept **any** `mimeType` YouTube returns, including `audio/webm; codecs="opus"` — which Android's own scoring explicitly prefers when available. **`AVFoundation`/`AVPlayer` does not support WebM containers or Opus decoding** (a general iOS platform limitation, not something in this repo's source — flagged here as an actionable risk, not a confirmed-from-source fact). The direct-URL client tier iOS currently relies on (VisionOS/AndroidVR/TVHTML5-embedded) is less likely to return WebM/Opus than the `WEB_REMIX` client Android prefers, but this is not guaranteed. **Recommend adding an explicit codec allow-list to iOS's format selection** (prefer/require `audio/mp4` + `mp4a`/AAC, exclude `audio/webm`/opus) as a Phase 1 fix — this is an iOS-specific correction Android's own code doesn't need.

## 5. Persistence: One Recommendation, Justified

### 5.1 What the Android schema actually demands (from V1 §14, restated for this decision)
18 tables + 3 views, **ordered** many-to-many joins (`song_artist_map.position`, `song_album_map.index`, `album_artist_map.order`, `playlist_song_map.position`), and — critically — **hand-written multi-line SQL with `UNION`s and correlated subqueries** for quick-picks/recommendations/stats (e.g. `quickPicks(now)`: a union of last-5-played + top-5-by-7-day-playtime + top-10-all-time, joined against a `related_song_map` referral-count subquery). 38 versions of migration history, though only the *current* (v38) shape needs replicating.

### 5.2 SwiftData-only
- **Hard blocker, not a soft trade-off**: `SwiftData` requires **iOS 17+**. This project's `project.yml` declares `deploymentTarget.iOS: "15.0"`. Recommending SwiftData means either raising the deployment target (a real product decision, not a technical detail) or abandoning SwiftData — I'm not going to paper over this with "SwiftData is nice" framing.
- Even setting that aside: `#Predicate` cannot express `UNION`s or correlated subqueries. The quick-picks/stats queries would have to be pulled into memory and recomputed in Swift, losing DB-level efficiency, and there's no supported "drop to raw SQL" escape hatch within SwiftData's own store.
- Ordered many-to-many is achievable (a stored `Int` position property + manual sort) but not first-class.

### 5.3 GRDB-only
- Works from iOS 11+ — no deployment-target conflict with the existing `project.yml`.
- **Full raw SQL support** — the quick-picks/stats `UNION`/correlated-subquery queries can be ported near-verbatim from the Room `@Query` SQL strings already documented in V1 §14, not reimplemented from scratch in Swift.
- `DatabaseMigrator` maps directly onto Room's `Migration`-object pattern conceptually (imperative, versioned steps) — even though (consistent with V1's recommendation) the practical plan is to target the current v38 shape rather than replay all 38 migrations, GRDB gives a proven path if schema evolution is needed later.
- Associations support ordered many-to-many via junction tables with explicit `ORDER BY` on the stored position/index/order columns — a direct match for Room's `sorted_song_artist_map`/`sorted_song_album_map` views.
- `ValueObservation` (Combine/`AsyncSequence`-compatible) is a direct analog to Room's `Flow`-returning DAO methods — no reactivity loss versus SwiftData.
- Trade-offs, stated plainly: third-party SPM dependency (acceptable for a personal sideload, not an App Store submission concern here), more boilerplate than SwiftData's macros (manual `Codable`/`FetchableRecord`/`PersistableRecord` conformances), no native SwiftUI `@Query` (GRDB's companion `GRDBQuery` package or a manual `ValueObservation`-to-`@Published` bridge substitutes).

### 5.4 Hybrid (SwiftData + GRDB)
**Explicitly rejected, not "possible but let's consider it."** Two ORMs pointed at conceptually the same entity graph means two migration histories, two query surfaces, and an ambiguous source of truth on every write — exactly the "overlapping database layers" the task explicitly says not to casually propose. There is no part of the Android schema that cleanly partitions into "simple enough for SwiftData" vs. "needs GRDB" in a way that would keep the two stores independent; the quick-picks queries alone touch `song`, `event`, and `related_song_map` — tables that would otherwise need to live in the "simple" SwiftData store, dragging the SQL-dependent logic across both.

### 5.5 Recommendation: **GRDB-only.**
Single database layer, single migration history, single query surface, iOS 15+ compatible (no forced deployment-target bump), and capable of porting Android's actual hardest queries (the `UNION`/correlated-subquery ones) faithfully instead of working around a query-language ceiling. The cost — more manual boilerplate, no `@Query` macro — is real but bounded and known; the SwiftData version-15-vs-17 blocker and query-expressiveness ceiling are not.

## 6. `AVAssetDownloadTask` Compatibility — Verified Incompatible

Per §3.4's confirmed findings: Android's downloads are **plain progressive HTTP(S) byte-range GETs against a resolved CDN URL, non-DRM, no HLS/DASH manifest, raw unmodified container bytes** (WebM/Opus or MP4/AAC, whichever the format-scoring picked). `AVAssetDownloadTask` is Apple's API for downloading **HLS (`.m3u8`) streams, optionally FairPlay-protected** — it has no mode for downloading an arbitrary progressive MP4/WebM URL. **It is not compatible with this app's actual download model**, full stop.

**Correct architecture**: a background `URLSession` (`URLSessionConfiguration.background(withIdentifier:)`, so downloads survive app suspension/termination) driving `URLSessionDownloadTask` against the same resolved stream URL `StreamResolver` already produces for playback, writing into a `FileManager`-managed cache directory split mirroring Media3's two-cache model:
- A **bounded, evictable** streaming-cache directory (mirrors `playerCache`/`LeastRecentlyUsedCacheEvictor`).
- An **unbounded, permanent** downloads directory (mirrors `downloadCache`/`NoOpCacheEvictor`), keyed by video ID (mirroring `setCustomCacheKey`).

`URLSessionDownloadTask` natively supports resume data for interrupted downloads, a reasonable fit given Android's own "cache-hit checks exact byte-range coverage" semantics don't need to be replicated exactly — a simpler "resume from `resumeData` or restart" model suffices. State tracking (`isDownloaded`/`dateDownload`) maps onto scalar columns on the GRDB `Song` record, exactly as they are scalar columns on Android's `song` table (not a separate table on either platform) — **and note the codec-allow-list fix from §4 applies equally to downloads**, since a downloaded WebM/Opus file would be just as unplayable as a streamed one.

## 7. Correcting "No-Mac-Required Workflow"

V1's README-derived framing was too broad. Precisely:

| Capability | No-Mac-required? | Detail |
|---|---|---|
| **CI build capability** | **Yes** | Confirmed real — GitHub Actions `macos-latest` compiled commit `da11574` successfully (§1). Costs nothing but a GitHub account and a push. |
| **Local native development** (Xcode editing/debugging/SwiftUI previews) | **No** | Xcode itself is macOS-only; there is no substitute that gives the live-preview/breakpoint/Instruments experience. Editing `.swift` files blind (as this audit and the prior session both did) is not equivalent to this. |
| **Code signing** | **Mostly, with a catch** | A provisioning profile can be created purely via the Apple Developer web portal without a Mac, *if* a distribution certificate already exists. Generating that initial `.p12` certificate is conventionally done via Keychain Access on a Mac; it's technically possible via `openssl` without one, but is not a beginner-friendly path. **Practically: expect to need at least brief access to a Mac (owned, borrowed, or a cloud-Mac rental) once, to mint the first certificate** — after that, CI can reuse the stored secret indefinitely. |
| **IPA generation** | **Yes, once signing secrets exist** | `archive-ipa` is a real, functional CI job (confirmed by reading the workflow) — it has just never run in this repo because no `IOS_TEAM_ID`/certificate secrets are configured yet. Once they are, no Mac is needed to produce a signed `.ipa` on every push. |
| **Physical-device debugging** (breakpoints, Instruments, live logs attached to a running instance) | **No** | Fundamentally requires Xcode + lldb attached to the device. No remote/cloud/Windows substitute exists for this. |
| **Runtime testing of background audio & WKWebView login** | **Partially yes** | Once a signed `.ipa` exists (via CI) and is installed on a real iPhone via a Windows-compatible sideloading tool (e.g. Sideloadly — note Apple Configurator, the "official" alternative, is itself Mac-only), **the user can manually exercise the app as an end user without a Mac** — lock the phone and listen for continued audio, attempt the YouTube login flow and see if it succeeds. What's **not** possible without a Mac is root-causing *why* something fails (no console output, no breakpoints, no network inspector) — only pass/fail observation. |

**Corrected summary**: "no-Mac-required" is true for *compiling* and, once initial signing exists, for *producing an installable build and manually exercising it on a real device* — it is false for the actual Xcode development/debugging loop and for diagnosing failures beyond "it did or didn't work."
